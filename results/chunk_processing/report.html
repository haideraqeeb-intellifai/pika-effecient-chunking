Saving paths compared

The CPU path overlaps chunk saves with VAE decoding and stitches four MP4s. The size-matched NVENC path streams decoded frames into one MP4 after all VAE calls.

Save-stage follow-up

These paths use the same four chunk inputs and sequential H3/VAE stages. They differ in when and how encoding starts. Each timing is one direct run.

Async saves versus deferred saves

Overlapping saves produced a ready video in 406.247 s. Waiting until all decodes finished, then starting four CPU encodes together, took 412.678 s including the same final stitch: 6.431 s slower. The deferred encodes occupied 9.683 s after decoding; the async workflow waited 4.111 s for saves at the end.

Original NVENC, unconstrained size

One NVENC H.264 save took 3.266 s after decoding and produced the finished video in 405.090 s, with no merge. Its CQ20 output was 67.6 MB versus 25.2 MB for the CPU path (2.69× larger), so this setting does not meet the file-size constraint.

NVENC tuned to CPU file size

NVENC p5 with VBR at 3.7 Mb/s, full-resolution multipass, and adaptive quantization took 3.789 s to save one MP4 after decoding. The direct run finished in 404.077 s with a 24.50 MB file, below the CPU path's 25.18 MB. It finished 2.170 s sooner than async saving in these single runs. A few seconds of difference needs repeated runs before treating it as a stable speed win.

Same-source codec check

To remove H3 run variation, the same decoded CPU-path MP4 was re-encoded once with each encoder. x264 veryfast CRF20 produced 23.08 MB, 46.580 dB PSNR, and 0.993289 SSIM versus that common source. NVENC p5 at 3.5 Mb/s produced 22.75 MB, 46.532 dB, and 0.992967. Both results include a second lossy encode, so this check compares encoders under the same input rather than measuring raw VAE output quality.

How to read these numbers

Timing basis

All 9 table values are timed full generation runs on the same single RTX 5090. The async-save graph waits for every H3 sampler before VAE decoding and moves the four latents to CPU at that barrier. In its direct run, the chunk execution order was 4 → 3 → 2 → 1. ComfyUI loads VAE weights for decoding and dynamically offloads H3 weights as needed; the graph has no explicit complete-unload step.

Image comparison

FFmpeg PSNR and SSIM filters compare aligned, decoded video frames against the separate-request baseline. All 9 complete outputs contain 1,186 frames at 1080 × 1920 and 24 fps. Baseline is the reference (SSIM 1.0; PSNR would be infinite). The decoded audio stream matches the reference exactly in all outputs.

What PSNR and SSIM mean here

They measure similarity to one baseline render, not artistic quality. A repeated unchanged serial run also differs from that baseline, so small metric differences can reflect generation or encoding variation. The timings are single-run observations; differences of a few seconds need repeated runs to establish a stable ranking.

Stitch and source

Final stitching is timed separately and added for paths with chunk MP4s; both NVENC paths have zero stitch time. The four chunk durations yield 293, 295, 290 and 308 output frames.
